# Матриця контролю доступу — ЛР 4

## Політика відмови

Для чужого ресурсу використовується політика **404 Not Found**.

Причина: звичайний користувач не повинен отримувати підтвердження того, що чужий ресурс взагалі існує. Тому для чужого та неіснуючого ресурсу API має повертати однакову відповідь.

Політика застосована однаково до `details`, `update` і `delete`: умова власника входить безпосередньо до `Where`-предиката запиту, тому чужий і неіснуючий `id` дають однаковий результат (`null` → `404 Problem Details` «Інцидент не знайдено»). Чужий рядок навіть не завантажується в пам'ять процесу.

Відмінність для дій без конкретного «чужого ресурсу»: коли заборонена сама дія для ролі (перегляд списку, пошук, зведення, `triage`, internal comment), повертається `403 Forbidden`, оскільки приховувати існування нічого — сам маршрут не є секретом.

## Основні правила

- Reporter може працювати тільки зі своїми інцидентами.
- Однакова роль Reporter не означає доступ до ресурсу іншого Reporter.
- Analyst може читати інциденти для аналізу.
- Analyst не отримує автоматичного права змінювати content або видаляти інциденти.
- Analyst може виконувати тільки передбачений перехід `New → Triaged`.
- Administrator не отримує права на всі операції лише через назву ролі. Якщо право прямо не визначено правилами роботи, використовується deny.
- `OwnerUserId`, role, status та інші поля під керуванням сервера не повинні визначатися клієнтом.
- Усі рішення про доступ приймаються на сервері. Приховування кнопки або іншого елемента інтерфейсу не є захистом.

## Другий знайдений дефект доступу

Під час огляду data-access points (A-01) виявлено, що перевірка дубліката `title` при створенні інциденту (`POST /api/incidents`) шукала збіг серед усіх інцидентів системи, незалежно від власника. Це дозволяло будь-якому Reporter дізнатись про існування чужого активного інциденту з конкретним `title` через код відповіді (`409 Conflict` замість `201 Created`), хоча `GET /api/incidents/{id}` для того самого ресурсу коректно повертав `404`. Різні endpoint-и давали суперечливі сигнали про існування одного й того самого ресурсу.

**Стан до.** Відтворено експериментально: Bob створив інцидент з унікальним `title`; Alice спробувала створити інцидент з тим самим `title` і отримала `409 Conflict`, хоча не є власником і не має права бачити цей інцидент.

**Першопричина.** Предикат `AnyAsync` у `Lab02Endpoints` порівнював лише `Title` і статус, без умови `OwnerUserId`, тобто не враховував суб'єкта.

**Виправлення.** До перевірки дубліката додано умову `OwnerUserId == ownerUserId` — унікальність `title` тепер рахується в межах власних інцидентів кожного користувача окремо.

**Стан після.** Alice й Bob можуть мати активні інциденти з однаковим `title` одночасно; повторна перевірка Alice дала `201 Created` замість `409`. Автоматичний тест `A02_DuplicateTitleAcrossDifferentOwners_DoesNotLeakExistence` проходить і прибирає створені інциденти у `finally`.

## Залишковий ризик

1. **CSRF.** Усі mutating-endpoint-и (`PUT`, `DELETE`, `POST …/triage`) захищені автентифікацією та перевіркою власника/ролі, але не мають окремого CSRF-захисту (anti-forgery token або `SameSite=Strict`). Авторизація на рівні ресурсу (owner-check) і захист від CSRF — незалежні рівні захисту, і перший не компенсує відсутність другого. Це свідомо задокументований навчальний борг ЛР 3, який закривається в ЛР 6.
2. **Побічні канали існування ресурсу.** Політика 404 узгоджена для `details`, `update`, `delete` і перевірки дубліката. Обмеження: для дій, закритих за роллю (`triage`, internal comment, list), повертається `403`; це не розкриває чужих ресурсів, але розкриває наявність самого маршруту, що є прийнятним.
3. **Роль у cookie.** Роль потрапляє до principal під час login і зберігається у виданій cookie. Зміна ролі в БД діє лише після повторного входу (або оновлення security stamp), тому відкликання привілеїв не миттєве.
4. **Concurrent transitions.** Перехід `New → Triaged` перевіряє статус і зберігає зміну без optimistic concurrency/version check, тому два одночасні виклики теоретично можуть обидва пройти перевірку. Сценарій від викладача не надавався, тому захист не реалізовано.
5. **Audit denied privileged action.** Структурована подія `authorization.denied` для відмови у `triage` не реалізована в поточному стані; відмова для Reporter повертає `403`, але рядка аудиту з `traceId` немає.
6. **Адміністративні права.** Administrator навмисно не має жодних додаткових прав (least privilege): право, не назване прямо в предметному правилі, є deny. Це зменшує ризик, але потребує окремого рішення, якщо адміністративні функції з'являться.
7. **Не охоплено.** Batch/export endpoint-ів у проєкті немає, тому не перевірялись.
