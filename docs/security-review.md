## Advanced variant (а): виявлення перебору відмов

Єдиний фільтр `AuthorizationDenialFilter` підключено до маршрутів ЛР 4 (details, update, delete, triage, внутрішній коментар, list, search, summary) і до create. Кожна відмова (403/404) пише запис категорії `Audit`: subject, action, resource, result, time, traceId. П'ята відмова одного користувача за 60 с дає подію безпеки `authorization.denied.burst` (одну на вікно), далі запити цього користувача отримують 429 `authorization-denied-burst` з `Retry-After` до кінця вікна. Partition: id користувача.

Рішення за умовами погодження (`docs/evidence/advanced-variant-agreement.md`):
1. Для list/search/summary відмовою є лише заборона ролі; фільтрація «лише власні записи» не є відмовою.
2. 404 для неіснуючого id рахується як відмова, бо ЛР 4 повертає однакову 404 для чужого й неіснуючого запису.
3. Logout без фільтра, доступний під час блокування; 429 відрізняється від 429 limiter пошуку типом Problem Details і `Retry-After`; дозволена мутація під 429 не змінює стан (є тест).
4. Подія burst пишеться один раз за вікно.
5. Вікно фіксоване (від першої відмови); у тестах власний fake вбудованого `TimeProvider`, без нових пакетів.
6. Лічильник потокобезпечний, прострочені partition вилучаються.

Обмеження: лічильник у пам'яті одного екземпляра (див. залишкові ризики).

## Залишкові ризики

Див. розділ «Залишкові ризики» в `docs/threat-model.md`: login CSRF, лічильники в пам'яті, відсутність блокування акаунта, enumeration при реєстрації, строк cookie, CSP без `base-uri`/`form-action`, журнали лише в консоль, фіксований HTTPS-порт.

## Висновок

Перевірено межі browser→API, API→PostgreSQL, repository→build, environment→configuration. Знайдено три прогалини в журналюванні й транспорті, усі усунені та закриті регресійними тестами. Відомі обмеження зафіксовано як прийняті ризики. Повний регресійний пакет (85 тестів) проходить.
