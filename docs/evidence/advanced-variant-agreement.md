## Запропонований варіант (а): виявлення перебору відмов

Один helper викликають усі захищені маршрути ЛР 4 (details, update, delete, triage, internal comment, list, search, summary). Він пише audit-запис `authorization.denied`: subject, action, resource, result, час, traceId. Якщо один subject отримує 5 відмов за 60 с, пишемо security event `authorization.denied.burst`, а далі його запити до кінця вікна отримують 429. Partition = id користувача, тож Alice не впливає на Bob, а після вікна доступ відновлюється. Журнал: structured-запис у `ILogger` (окрема категорія `Audit`, окремо від diagnostic log), тест читає його через in-memory `ILoggerProvider` у тестовому хості; нових залежностей, endpoint-ів і міграцій немає. Тести: параметризований `[Theory]` за матрицею доступу, поріг (5-та відмова → burst, далі 429), ізоляція Alice/Bob, скидання після вікна (у тесті вікно скорочене), позитивна регресія (дозволена дія запису не створює). Межа: лічильник у пам'яті одного екземпляра API, це піде в residual risk.

## Відповідь викладача

У такому описі погоджую як advanced variant ЛР 6. Під час реалізації врахуйте:
1. Для list/search/summary відмовою вважається лише заборона маршруту для ролі. Фільтрація «лише власні записи» — не відмова, audit-запису там немає.
2. Явно вирішіть і задокументуйте, чи враховується в лічильник 404 для неіснуючого id, а не лише для чужого.
3. Logout під час блокування лишається доступним. Ваш 429 має відрізнятися від 429 наявного search limiter (ProblemDetails type або Retry-After). Під час 429 дозволена мутація не змінює стан — додайте це в тест.
4. Подія burst пишеться один раз за вікно, а не на кожен наступний 429.
5. Укажіть, вікно фіксоване чи ковзне. Для тесту скидання підставте власний fake вбудованого `TimeProvider`, без нових пакетів.
6. Лічильник має бути потокобезпечним, а старі партиції — вилучатися.
7. Цю відповідь збережіть у доказах звіту. Погодження стосується лише розширення: решта вимог відмінного рівня (третя власна finding, e2e REG-CSRF-01, CSP тощо) лишається.

## Мої рішення за зауваженнями

| № | Рішення |
|---|---|
| 1 | Відмова = заборона маршруту для ролі (403) або чужий/відсутній запис (404 за політикою ЛР 4). У list/search/summary фільтр «лише власні» не рахується, audit-запису немає. |
| 2 | 404 для неіснуючого id **рахується** так само, як для чужого запису: за політикою ЛР 4 відповідь однакова, тож окреме правило відкрило б, чи існує запис. Ризик: користувач, що 5 разів ввів неіснуючий id, блокується на вікно. |
| 3 | Logout винесено з-під блокування. 429 має ProblemDetails `type` = `.../authorization-denied-burst` і `Retry-After`; search limiter має інший `type`. Тест: мутація під час 429 не змінює стан. |
| 4 | Прапорець «burst записано» у partition: подію пишемо один раз за вікно. |
| 5 | Вікно **фіксоване**, 60 с від першої відмови. Межа: 5 відмов наприкінці одного вікна й 5 на початку наступного дають 10 за короткий час (residual risk). У тесті використано власний `FakeTimeProvider : TimeProvider`. |
| 6 | `ConcurrentDictionary` + блокування на partition; прострочені partition вилучаються під час звернень. |
