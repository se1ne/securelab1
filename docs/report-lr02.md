## 2. Основні виконані зміни

1. Реалізовано `POST /api/incidents` із окремим request DTO `CreateIncidentRequest`.
2. Реалізовано server-side validation для полів `title`, `description`, `severity` та `occurredAtUtc`.
3. Для `severity` виконуються дві перевірки: `Enum.TryParse` і `Enum.IsDefined`, що не дозволяє приймати числові значення, відсутні в enum.
4. Поля `title` і `description` нормалізуються через `Trim()`, а `occurredAtUtc` перед записом приводиться до UTC.
5. Реалізовано cross-field правило: для `High` або `Critical` поле `description` після `Trim()` повинно містити щонайменше 40 символів.
6. Реалізовано предметний конфлікт: повторне створення активного інциденту з таким самим `title` повертає `409 Conflict`.
7. Server-managed поля `id`, `ownerUserId`, `status`, `createdAtUtc` та `updatedAtUtc` встановлюються виключно сервером.
8. Досліджено навмисно вразливий пошук `GET /api/incidents/search` на окремому vulnerable commit.
9. Усунуто першопричину SQL injection: пошук переписано з raw SQL на LINQ та `EF.Functions.ILike`.
10. Для literal substring search реалізовано екранування символів `%`, `_` та `\`.
11. Параметр `sortBy` реалізовано через серверний `switch` із allowlist значень `createdAtUtc`, `severity` та `status`.
12. Для стабільного сортування використовується другий ключ `Id`, а кількість результатів обмежено через `Take(50)`.
13. Додано автоматичні регресійні та security-тести.
14. Для відмінного рівня реалізовано додаткове предметне правило T-10, повний огляд data-access points A-01 та перевірку ризику overposting A-02.
15. Після останніх змін усі 12 автоматичних тестів завершилися успішно.

## 3. Контрольні точки

### CP-01. Перевірений контракт створення

Для створення інциденту використовується окремий тип `CreateIncidentRequest`, який містить лише ті поля, які клієнту дозволено передавати: `Title`, `Description`, `Severity`, `OccurredAtUtc`.

Поля `Id`, `OwnerUserId`, `Status`, `CreatedAtUtc` та `UpdatedAtUtc` до request DTO не входять і встановлюються сервером.

Під час перевірки було підтверджено:

- порожній `title` повертає `400 Bad Request`;
- невідоме значення `severity` повертає `400`;
- `severity = "7"` також повертає `400`, оскільки одного `Enum.TryParse` недостатньо і додатково використовується `Enum.IsDefined`;
- відсутній `occurredAtUtc` повертає `400`;
- дата, що перевищує поточний UTC-час більш ніж на 5 хвилин, повертає `400`;
- зайві поля `id`, `ownerUserId` та `status`, передані в JSON, не можуть підмінити server-managed значення;
- для `High` опис довжиною 39 символів повертає `400`, а опис довжиною 40 символів проходить перевірку;
- повторний активний `title` повертає `409 Conflict`.

Маршрут обробки:
`JSON → request DTO → server-side validation → business rule → data-access → response DTO / Problem Details`.

### CP-02. Доказ першопричини SQL injection

Vulnerable commit:

`1a1bb43f747935b8a5e84228a15be668d0c5ef0a`

На цьому стані пошук `GET /api/incidents/search` формував SQL із недовіреного значення `q`.

Було виконано чотири контрольні сценарії:

- звичайний пошук `USB` повернув один запис «Перевірка USB навчальної мережі»;
- пошук неіснуючого значення `zz-no-match` повернув `[]`;
- контрольний read-only сценарій призвів до небажаного розширення множини та повернув усі наявні на той момент записи;
- легітимний пошук `O'Brien` завершився `500 Internal Server Error`.

У логах БД було видно, що значення пошуку не передавалося окремим SQL-параметром, а входило до сформованого SQL-тексту.

Першопричина полягала не в конкретному наборі символів, а у змішуванні недовірених даних зі структурою SQL-команди.

### CP-03. Перевірений механізм виправлення

Vulnerable commit:

`1a1bb43f747935b8a5e84228a15be668d0c5ef0a`

Fixed commit:

`8f0d08ebab160f30f2f3d1cab7f3af24603e9348`

Excellent-level commit:

`ecfec822ed726d126000a96c18d7dbe61c94a45c`

Security diff:

`src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs`  
48 рядків додано, 12 видалено.

У vulnerable commit значення параметра `q` безпосередньо включалося до SQL-тексту, через що контрольний read-only сценарій змінював логіку запиту та розширював множину результатів.

У fixed commit пошук переписано на LINQ з `EF.Functions.ILike`. Значення `pattern` передається PostgreSQL окремим параметром. Для literal substring search символи `%`, `_` та `\` екрануються.

Параметр `sortBy` більше не може довільно впливати на структуру SQL. Сервер обирає один із трьох дозволених варіантів через `switch`:

- `createdAtUtc`;
- `severity`;
- `status`.

Після виправлення:

- той самий контрольний сценарій S-02 повертає порожню множину;
- пошук `USB` повертає рівно один очікуваний запис;
- пошук значення з легітимним апострофом більше не спричиняє `500`;
- невідоме значення `sortBy` повертає `400`;
- автоматичний S-02 перевіряє не лише код відповіді, а й точну множину результатів.

Після останніх змін виконано повний запуск автоматичних тестів:

`total: 12, failed: 0, succeeded: 12, skipped: 0`.

## 5. S-01 / S-02 — дослідження та виправлення SQL injection

### 5.1. Контекст і гіпотеза

Endpoint пошуку отримує недовірені параметри `q` та `sortBy`.

До виправлення існував ризик того, що введене клієнтом значення стане частиною структури SQL-команди.

### 5.2. Стан до виправлення

На vulnerable commit `1a1bb43f747935b8a5e84228a15be668d0c5ef0a` значення `q` використовувалося під час формування raw SQL.

Було підтверджено:

- нормальний запит працює;
- неіснуюче значення дає порожню множину;
- контрольний read-only сценарій змінює логіку запиту;
- звичайний апостроф порушує синтаксис SQL та спричиняє `500`.

### 5.3. Першопричина

Проблема виникала через те, що дані користувача змішувалися зі структурою SQL до передачі команди СУБД.

Фільтрація окремих символів не усунула б сам механізм уразливості, оскільки структура SQL все одно залежала б від введення користувача.

### 5.4. Виправлення

У fixed commit:

- raw SQL замінено на LINQ;
- пошук реалізовано через `EF.Functions.ILike`;
- пошуковий шаблон передається БД окремим параметром;
- `%`, `_` та `\` екрануються;
- `sortBy` проходить через server-side allowlist;
- результати обмежено `Take(50)`;
- додано стабільний другий ключ сортування `Id`.

### 5.5. Retest

Після виправлення:

- контрольний сценарій більше не розширює вибірку;
- `S-02` повертає `[]`;
- звичайний `USB` знаходить один очікуваний запис;
- легітимний апостроф працює як звичайне пошукове значення;
- автоматичний regression test перевіряє точну множину результатів.

## 6. A-01 — огляд data-access points

Після виправлення було виконано пошук raw SQL конструкцій:

`git grep -n -e FromSqlRaw -e ExecuteSqlRaw -e "ORDER BY" -- src tests`

Було знайдено лише один `ExecuteSqlRawAsync` у `DatabaseBootstrap.cs`.

Додаткові пошуки:

`git grep -n -F '$"SELECT' -- src tests`

`git grep -n -F '+ query' -- src tests`

не повернули збігів.

Для відмінного рівня додатково переглянуто LINQ, `DbContext` та service-based точки доступу до БД.

| Файл / метод | Категорія | Висновок |

## 7. T-10 — додаткова предметна перевірка

Для відмінного рівня було додано нове правило:

`description` після `Trim()` не може повністю дорівнювати `title`.

У разі порушення:

- код відповіді: `400 Bad Request`;
- ключ помилки: `description`.

Було виконано два сценарії:

1. `title` і `description` однакові — сервер повернув `400`.
2. `title` і `description` різні — сервер успішно створив ресурс і повернув `201 Created`.

Таким чином підтверджено як негативну, так і позитивну межу додаткового предметного правила.

## 8. A-02 — перевірка overposting

Під час A-01 другого SQL-дефекту не було виявлено, тому для A-02 було обрано ризик overposting / mass assignment.

Потенційний ризик полягав у можливості клієнта передати server-managed поля:

- `id`;
- `ownerUserId`;
- `status`;
- `createdAtUtc`.

Якби request DTO повторював entity, клієнт міг би потенційно підмінити ці значення.

У поточній реалізації `CreateIncidentRequest` цих властивостей не містить.

Автоматичний тест відправляє JSON із зайвими значеннями:

- власний `id`;
- інший `ownerUserId`;
- `status = Closed`;
- довільний `createdAtUtc`.

Після створення перевіряється, що:

- створений `id` не дорівнює надісланому;
- `status` дорівнює `New`;
- власником є «Аліса Коваль».

Таким чином відтвореного mass-assignment дефекту в реалізації не виявлено. Ризик локалізовано, заблоковано контрактом request DTO та підтверджено автоматичним тестом.

## 12. Висновок

У лабораторній роботі було реалізовано серверну валідацію контракту створення інцидентів, відокремлено дозволені клієнтські поля від server-managed значень та реалізовано коректну семантику HTTP-відповідей для помилок валідації і предметних конфліктів.

На окремому vulnerable commit було досліджено механізм SQL injection у локальному навчальному endpoint пошуку. Було встановлено, що першопричиною є безпосереднє включення недовіреного значення до SQL-тексту. Після цього raw SQL пошук було замінено на LINQ з `EF.Functions.ILike`, а dynamic sorting обмежено server-side allowlist.

Після виправлення повторний security-сценарій більше не змінює логіку запиту, звичайний пошук і пошук із легітимним апострофом працюють коректно. Проведено повний огляд data-access points, додано власну предметну перевірку T-10 та автоматично підтверджено захист від overposting.

Після всіх змін виконано повний набір автоматичних перевірок: 12 тестів із 12 завершилися успішно. Отриманий стан відповідає вимогам відмінного рівня лабораторної роботи.
