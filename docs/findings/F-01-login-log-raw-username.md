# F-01. Журнал входу записує введене ім'я користувача як є

| Поле | Значення |
|---|---|
| Ідентифікатор | F-01 |
| Тип | Небезпечне журналювання (A09:2021, CWE-532) |
| Серйозність | Low |
| Компонент | `POST /api/auth/login` (Lab03Identity.cs) |
| Статус | Виправлено, повторна перевірка пройдена |

## Опис

Обробник входу записував у журнал значення поля `userName` без змін, також при невдалому вході. Це значення контролює той, хто надсилає запит.

## Як виявлено

Огляд журналів у сценаріях «успішний» і «невдалий вхід» (рисунки 59–60). Перевірка: вхід із неіснуючим іменем `nobody-user-123` → 401, у журналі `Authentication event login: user nobody-user-123, result failure` (рисунки 78–79).

## Ризик

1. Користувач може помилково ввести пароль у поле імені, і пароль опиниться в журналі.
2. Довільний текст з керуючими символами або дуже довгий рядок потрапляє в журнал (підміна записів, роздування журналу).
3. Журнал стає джерелом чутливих даних, до якого мають доступ ширше, ніж до бази.

## Виправлення

Додано `LogSanitizer.Fingerprint`: перші 8 hex-символів SHA-256 від нормалізованого імені (`sha256:xxxxxxxx`). При невдалому вході та порожніх даних у журнал іде лише відбиток (`userRef`). При успішному вході пишеться ім'я підтвердженого користувача. Відбиток дозволяє зіставити кілька спроб з одним іменем, але не зберігає введений текст.

## Повторна перевірка

1. Автоматично: `LoginLoggingTests` (REG-LOG-01): для неіснуючого імені, існуючого імені з хибним паролем і пароля, введеного в поле імені, журнал не містить ні імені, ні пароля; успішний вхід містить ім'я користувача без пароля. 85 тестів з 85 (рисунок 86).
2. Вручну: той самий запит → 401, у журналі `userRef sha256:70803aed` (рисунки 87–88).

## Залишковий ризик

Відбиток короткого імені можна підібрати перебором, якщо відомий журнал. Для навчального проєкту прийнято: мета — не зберігати введений текст, а не приховати існування конкретного імені від того, хто має журнал.
